# cleanpass

`cleanpass` працює з копіями однієї бази KeePassXC, які розійшлись. Він показує, чим копії відрізняються, і за вашою командою створює новий файл бази. Оригінали ніколи не змінюються.

Це один файл для кожної системи. Встановлювати нічого не треба, тому він може лежати на флешці поруч із базами. Команди описує довідка: `cleanpass --help`.

## Готовий файл

Реліз виходить сам, коли в `main` зливається нова функція чи виправлення (розділ «Релізи» нижче). Тег релізу має вигляд `v0.2.1`. Завантажте файл для своєї системи разом із контрольними сумами:

```
gh release download <тег> --repo yberkut/cleanpass --pattern <файл> --pattern SHA256SUMS
```

| Система | Файл |
| --- | --- |
| Linux, x86-64 | `cleanpass-linux-amd64` |
| Linux, ARM | `cleanpass-linux-arm64` |
| macOS, Apple Silicon | `cleanpass-darwin-arm64` |
| macOS, Intel | `cleanpass-darwin-amd64` |
| Windows, x86-64 | `cleanpass-windows-amd64.exe` |
| Скрипт ручної перевірки | `cleanpass-manual-check.sh` |

Перевірте SHA-256. Команда залежить від системи:

```
sha256sum -c --ignore-missing SHA256SUMS            # Linux
shasum -a 256 -c --ignore-missing SHA256SUMS        # macOS
Get-FileHash cleanpass-windows-amd64.exe            # Windows: порівняйте з рядком у SHA256SUMS
```

На Linux і macOS завантажений файл треба зробити виконуваним: `chmod +x <файл>`.

## Збірка з вихідного коду

Потрібен лише Go 1.27 або новіший. Компілятор C не потрібен. Команди однакові для Linux, macOS і Windows:

```
gh repo clone yberkut/cleanpass
cd cleanpass
go build ./cmd/cleanpass
```

Результат лежить у поточній директорії: `cleanpass`, а на Windows `cleanpass.exe`. Код не використовує cgo, тому це статичний файл навіть без `CGO_ENABLED=0`.

Усі цілі з одного ПК збирає така команда. Вона теж однакова для трьох систем:

```
go run ./tools/dist
```

У директорії `dist` з'являються усі файли з таблиці вище і `SHA256SUMS`. Збірка йде з `CGO_ENABLED=0`, навіть якщо оболонка задає інше значення. Реліз створює та сама команда.

## Запуск із флешки

Покладіть файл на флешку поруч із базами і запустіть його звідти:

```
./cleanpass-linux-amd64 --help
```

- Права адміністратора не потрібні.
- Тула не пише конфігів. На диск вона записує лише новий файл бази, шлях до якого ви вказали самі.
- Якщо флешка змонтована без права запуску, скопіюйте файл у домашню директорію і запустіть його там.

Дві зовнішні програми потрібні лише для окремих можливостей:

- `keepassxc-cli` незалежно перевіряє результат злиття. Без нього тула чітко попереджає, що зовнішньої перевірки не було.
- `ykman` від Yubico потрібен лише для баз із YubiKey. Без нього тула каже, що зробити.

## Бази з YubiKey

Слот ключа задається окремо для кожної копії, опцією після її файла або відповіддю на запитання після невдалої спроби:

```
cleanpass compare a.kdbx --yubikey 2 b.kdbx --yubikey 1
```

Тула викликає `ykman otp calculate` і просить торкнутись ключа перед кожним викликом, який може чекати на дотик. Скільки разів торкатись:

- Один дотик на кожну копію. Копії з однаковою сіллю потребують одного дотику на всіх, і нова спроба після неправильного пароля нового дотику не потребує.
- Один дотик на запис результату, бо новий файл має нову сіль.
- Кілька дотиків на перевірку справжнім KeePassXC, бо кожен виклик `keepassxc-cli` просить ключ окремо. Перед перевіркою тула каже, скільки їх буде.

Формат KDBX 3 з YubiKey тула не відкриває. Сумісність із KeePassXC на справжньому ключі ще не підтверджена: її перевіряє лише людина.

## Обмеження macOS

- Файл не підписаний сертифікатом Apple, тому система може питати дозвіл на запуск. Якщо macOS не запускає файл, зніміть позначку карантину: `xattr -d com.apple.quarantine <файл>`. Інший спосіб: `System Settings` → `Privacy & Security` → `Open Anyway`. Назви пунктів залежать від мови системи.
- CI запускає файл лише на Apple Silicon. Файл для Intel збирається, але його ніде не запускають.

## Інші обмеження

- Файл для Windows теж не підписаний, тому SmartScreen може показати попередження.
- Git for Windows 2.55 дає програмам у mintty консоль Windows, тому тула там просить пароль і ховає його, як у Windows Terminal. Старіші версії Git Bash і будь-яка з `MSYS=disable_pcon` дають програмі канал замість консолі. Там пароль було б видно під час введення, тому тула не просить пароль і пояснює причину. Тоді запускайте її через `winpty cleanpass ...` або у Windows Terminal. Скрипт, який передає паролі через канал, працює всюди.
- Файл для Linux ARM CI теж лише збирає, але не запускає.

## Ручна перевірка

Справжній YubiKey і справжні бази перевіряє лише людина. Скрипт `scripts/manual-check.sh` проводить вас через це крок за кроком: у релізі він лежить поруч із файлами тули як `cleanpass-manual-check.sh`. Запустіть його у власному терміналі, а на Windows у вікні Git Bash:

```
bash cleanpass-manual-check.sh
```

Скрипт нікуди нічого не надсилає і не читає паролів: пароль іде з клавіатури прямо до тули чи до KeePassXC. Кроки зі справжніми базами необов'язкові. Підсумок наприкінці не містить ні паролів, ні шляхів, ні назв записів. Не запускайте скрипт через Claude чи іншу модель: без власного термінала він відмовляється працювати.

## Перевірка

CI запускає все це на кожен push на Ubuntu, macOS і Windows зі справжнім KeePassXC. Локально тести потребують `keepassxc-cli`:

```
go vet ./...
go test -timeout 60m ./...
```

Тести `cmd/cleanpass` можуть іти довше за типові для Go 10 хвилин, тому потрібна опція `-timeout`.

CI також перевіряє код для кожної з трьох систем: `go mod tidy -diff`, `go fix -diff` і `golangci-lint` v2 з налаштуваннями з `.golangci.yml`. На Linux він ще запускає тести `internal` з `-race`. Для цього потрібен cgo, тому лише цей крок збирає з `CGO_ENABLED=1`.

Результати приймальної перевірки і чесний перелік того, що лишилось не перевіреним, записані в `docs/acceptance.md`.

Копія бібліотеки `third_party/gokeepasslib` має власний `go.mod`. Її тести запускаються окремо, з її директорії: `go test ./...`. Що в ній змінено, описує `third_party/gokeepasslib/PATCHES.md`.

## Релізи

Зміни потрапляють у `main` лише через pull request. Кожне злиття запускає workflow `Release`: він проганяє весь CI, а тоді `git-cliff` читає коміти після останнього тега.

| Коміти після `v0.1.0` | Наступна версія |
| --- | --- |
| є `fix:` чи `perf:` | `v0.1.1` |
| є `feat:` | `v0.2.0` |
| є `!` перед `:` або `BREAKING CHANGE:` у тексті | `v0.2.0`, поки версія 0.x |
| лише `test`, `docs`, `refactor`, `ci`, `chore`, `build` | релізу немає |

Тому кожен коміт гілки має вигляд `тип: текст` або `тип(область): текст` (Conventional Commits). CI це перевіряє. Нотатки релізу складаються з тих самих комітів. Правила лежать у `cliff.toml`, а причини — у `docs/adr/0001-release-on-each-merge.md`.

Наступну версію і нотатки видно заздалегідь, якщо встановлено `git-cliff`:

```
git cliff --bumped-version
git cliff --unreleased --strip all
```

Кнопка «Run workflow» у `Release` робить усе, крім публікації.

GitHub не забороняє push у `main` для приватного репозиторію на безкоштовному плані. Тому після клонування ввімкніть hook, який забороняє це на вашому ПК:

```
git config core.hooksPath .githooks
```

Коміт, що потрапив у `main` без pull request, релізу не отримує: `Release` для нього червоний. Його випустить наступне злиття.
