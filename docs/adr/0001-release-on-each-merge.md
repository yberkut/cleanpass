# 0001. Реліз після кожного злиття в main

Статус: прийнято, 2026-11-05. Оновлено 2026-11-06: репозиторій став публічним, і заборону push у `main` тепер тримає ruleset GitHub (пункт 6).

## Контекст

Раніше реліз створював тег `v*`, поставлений руками. Людина сама обирала номер і не мала нотаток, крім тих, що GitHub збирає з назв pull request. Жодного релізу так і не вийшло.

Усі коміти репозиторію вже мають вигляд Conventional Commits (`feat:`, `fix:`, `test:` …). З них можна порахувати наступну версію і скласти нотатки без людини.

Спершу репозиторій був приватним, а план GitHub безкоштовним. Правила для гілок (rulesets, branch protection) тоді були недоступні: API відповідав `Upgrade to GitHub Pro or make this repository public`. 2026-11-06 репозиторій став публічним, і правила стали доступні.

## Рішення

1. Кожен push у `main` запускає `.github/workflows/release.yml`. Він проганяє весь CI, а тоді `git-cliff` читає коміти після останнього тега:
   - `fix` і `perf` піднімають patch: `v0.1.0` → `v0.1.1`;
   - `feat` піднімає minor: `v0.1.0` → `v0.2.0`;
   - зміна, що ламає сумісність (`!` перед `:` або `BREAKING CHANGE:` у тексті), поки версія 0.x, теж піднімає minor;
   - `test`, `docs`, `refactor`, `ci`, `chore`, `build` релізу не дають.
2. Правила і вигляд нотаток лежать у `cliff.toml`. Перший реліз — `v0.1.0`. Версію `v1.0.0` обирає людина: pull request ставить `breaking_always_bump_major = true` і містить зміну, що ламає сумісність.
3. Тег з'являється разом із релізом, коли всі файли вже зібрано. Збірка ставить тег лише локально, щоб `go build` записав версію у файли.
4. CI перевіряє, що кожен коміт гілки — Conventional Commit. Dependabot пише `fix(deps):` для модулів Go (patch-реліз) і `ci(deps):` для actions (без релізу).
5. Зміни йдуть у `main` лише через pull request, злиттям через merge commit. Squash і rebase вимкнено, тож кожне злиття — merge commit, а коміти гілки лишаються в історії для `git-cliff`.
6. Цю заборону тримає ruleset GitHub `main only through pull requests` для гілки за замовчуванням. Обійти його не може ніхто, навіть адміністратор:
   - зміни йдуть у `main` лише через pull request, схвалення не потрібне;
   - force push і видалення `main` заборонено.

   Зеленого CI перед злиттям ruleset поки не вимагає. Дві м'які речі лишились як друга лінія:
   - hook `.githooks/pre-push` зупиняє push у `main` ще на ПК, де його ввімкнено (`git config core.hooksPath .githooks`), і каже, що робити;
   - `release.yml` не робить релізу з коміту, який не є merge commit якогось pull request.

## Чому не інше

- semantic-release (Node): не вміє версій 0.x, перший реліз одразу `v1.0.0`. Він тягне Node і сотні пакетів npm у збірку менеджера паролів. Тег він ставить ще до завантаження файлів.
- release-please: реліз чекає окремого pull request з версією, а не виходить після кожного злиття.
- Лише hook, без правил GitHub: так було, поки репозиторій був приватним. `git push --no-verify` обходить hook, і push повз pull request було видно лише як червоний запуск `Release`.

## Наслідки

- Повідомлення комітів тепер визначають версію і нотатки. Неправильний тип коміту дає неправильну версію.
- CI на `main` іде один раз, усередині `Release`. Тригер `push` у `ci.yml` пропускає `main`.
- Релізи йдуть по одному. Якщо злиття прийшло під час релізу, воно чекає і потім випускає все, що ще не випущено.
- GitHub відхиляє push у `main` повз pull request. Такий push можливий, лише якщо хтось вимкне або змінить ruleset.
